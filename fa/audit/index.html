Cómo auditar qué datos envía una aplicación por Internet

Cualquier aplicación que se comunique con Internet puede enviar información fuera de tu equipo. Algunas conexiones son necesarias para que el programa funcione; otras pueden utilizarse para comprobar actualizaciones, registrar errores, recopilar estadísticas o transmitir datos que no esperabas compartir.

Esta guía te permitirá:

  • identificar todas las conexiones realizadas por una aplicación;
  • inspeccionar el contenido de las comunicaciones HTTP y HTTPS;
  • comprobar qué datos concretos salen del equipo;
  • relacionar cada envío con una acción realizada en la aplicación;
  • detectar conexiones que no hayan podido ser inspeccionadas;
  • elaborar un informe reproducible con los resultados.

El procedimiento sirve para TDownloader y para cualquier otra aplicación de escritorio instalada en Windows, macOS o Linux.

Importante: ninguna herramienta permite prometer una auditoría perfecta en todos los casos. Una aplicación puede utilizar certificate pinning, protocolos propietarios, cifrado adicional, procesos auxiliares o controladores del sistema. Esta guía no oculta esas limitaciones: una auditoría solo se considerará completa cuando todas las conexiones detectadas hayan podido inspeccionarse o justificarse.

Qué vamos a comprobar

Una auditoría de red tiene dos partes distintas.

1. Detectar las conexiones

Primero hay que averiguar:

  • qué servidores contacta la aplicación;
  • qué dominios y direcciones IP utiliza;
  • en qué momento se producen las conexiones;
  • qué proceso las inicia;
  • qué protocolo y puerto emplean;
  • cuánto tráfico se envía y se recibe.

2. Inspeccionar el contenido

Después hay que examinar cada petición para comprobar si contiene:

  • direcciones de correo;
  • nombres de usuario;
  • identificadores del dispositivo;
  • versión del sistema operativo;
  • versión de la aplicación;
  • estadísticas de uso;
  • mensajes o búsquedas;
  • nombres de archivos;
  • rutas del disco;
  • contenido de archivos;
  • cookies;
  • tokens de autenticación;
  • contraseñas;
  • claves privadas;
  • cualquier otro dato personal o potencialmente sensible.

Un firewall permite realizar la primera parte. Para la segunda necesitaremos un proxy de interceptación HTTPS.

Ver el destino no significa conocer los datos enviados.

Herramientas necesarias

Usaremos dos tipos de herramientas.

Herramienta principal: mitmproxy

mitmproxy es un proxy de interceptación capaz de mostrar solicitudes y respuestas HTTP y HTTPS. Incluye tres interfaces:

  • mitmproxy: interfaz de terminal;
  • mitmweb: interfaz visual abierta en el navegador;
  • mitmdump: versión orientada a consola y automatización.

En esta guía utilizaremos mitmweb, porque permite revisar las comunicaciones de forma visual.

mitmproxy puede interceptar HTTP, HTTPS, HTTP/2 y WebSockets, guardar las comunicaciones y mostrar su contenido. Para descifrar HTTPS, el dispositivo debe confiar temporalmente en el certificado local generado por mitmproxy.

Herramienta secundaria: monitor de conexiones

También necesitaremos una herramienta que muestre todas las conexiones realizadas por el proceso, incluso aquellas que mitmproxy no consiga descifrar. Algunas opciones son:

  • Windows: TCPView, Monitor de recursos o un firewall de aplicaciones.
  • macOS: Monitor de Actividad, nettop o un firewall de aplicaciones.
  • Linux: OpenSnitch, Portmaster, ss, lsof o Wireshark.

No es obligatorio utilizar una herramienta concreta. Lo importante es poder comparar la lista total de conexiones con las solicitudes que aparecen en mitmweb.

Parte 1. Preparar un entorno de prueba seguro

1. Utiliza datos ficticios

No realices la primera prueba con tu cuenta habitual ni con documentos personales. Crea, cuando sea posible:

  • una cuenta de prueba;
  • un perfil nuevo en la aplicación;
  • una carpeta temporal vacía;
  • archivos de prueba sin información real;
  • credenciales diferentes de las que utilizas habitualmente.

Durante la auditoría podrás ver tokens, cookies y otros datos de autenticación. No publiques las capturas sin ocultarlos.

2. Crea datos identificables

Para descubrir fácilmente si la aplicación transmite información local, utiliza valores únicos que puedas buscar después en el tráfico capturado. Por ejemplo:

Usuario:  AUDIT_USUARIO_20260712
Carpeta:  AUDIT_CARPETA_PRIVADA_20260712
Archivo:  AUDIT_ARCHIVO_SECRETO_20260712.txt
Contenido: AUDIT_CONTENIDO_NO_DEBE_ENVIARSE_20260712
Búsqueda: AUDIT_BUSQUEDA_UNICA_20260712

Estas cadenas funcionan como marcadores. Si una de ellas aparece en una petición, sabrás exactamente qué información ha enviado la aplicación y qué acción provocó el envío.

No utilices siempre los valores de este ejemplo. Añade una fecha o una secuencia aleatoria para que tus marcadores sean únicos.

Los marcadores únicos permiten descubrir si la app transmite nombres, rutas o contenidos.

3. Aísla la aplicación

La forma más fiable de evitar que el tráfico de otros programas se mezcle con el de la aplicación auditada es utilizar:

  • una máquina virtual;
  • un equipo secundario;
  • una cuenta nueva del sistema operativo;
  • o, como mínimo, cerrar navegadores, clientes de correo, sincronizadores y otras aplicaciones que utilicen Internet.

Una máquina virtual limpia es la opción más rigurosa. También permite restaurar el sistema después de instalar el certificado de interceptación.

Si no utilizas una máquina virtual, captura únicamente el proceso de la aplicación cuando la herramienta lo permita.

4. Desactiva interferencias

Antes de comenzar:

  • cierra la aplicación que vas a analizar;
  • cierra programas innecesarios;
  • pausa las sincronizaciones;
  • evita realizar otras actividades durante la captura;
  • anota la fecha, la hora y la versión exacta de la aplicación;
  • anota la versión del sistema operativo.

Parte 2. Instalar mitmproxy

Descarga mitmproxy únicamente desde su sitio oficial. Las instrucciones oficiales recomiendan:

  • Windows: utilizar el instalador oficial;
  • macOS: instalarlo mediante Homebrew o descargar los binarios;
  • Linux: descargar los binarios independientes oficiales.

Los paquetes incluidos en algunas distribuciones Linux pueden ir por detrás de la versión publicada por el proyecto.

Después de instalarlo, abre una terminal y ejecuta:

mitmweb

Se iniciará el proxy y se abrirá su interfaz visual en el navegador. Por defecto, el proxy escucha en:

127.0.0.1:8080

Parte 3. Instalar temporalmente el certificado

HTTPS cifra el contenido entre la aplicación y el servidor. Para mostrarlo, mitmproxy genera certificados locales y actúa como intermediario entre ambos extremos.

El certificado debe instalarse exclusivamente en el entorno utilizado para la auditoría.

Procedimiento recomendado

  1. Inicia mitmweb.
  2. Configura temporalmente el proxy del sistema con estos valores:
Servidor: 127.0.0.1
Puerto: 8080
  1. Abre un navegador.
  2. Visita:
http://mitm.it
  1. Selecciona tu sistema operativo.
  2. Descarga e instala el certificado.
  3. Cuando el sistema lo pregunte, autoriza su uso para identificar sitios web o conexiones TLS.

mitmproxy genera una autoridad certificadora diferente en cada instalación. El certificado permite que mitmproxy descifre las conexiones mientras esté instalado y el tráfico pase por el proxy.

Precauciones

  • No compartas la clave privada generada por mitmproxy.
  • No instales certificados proporcionados por terceros.
  • No dejes el certificado instalado permanentemente.
  • Elimina el certificado cuando termines la auditoría.
  • Realiza las pruebas con datos ficticios.
  • No utilices este entorno para banca, correo personal ni servicios sensibles.

El certificado debe eliminarse al terminar.

Parte 4. Comprobar que HTTPS puede inspeccionarse

Antes de abrir la aplicación auditada, comprueba que la configuración funciona.

  1. Mantén mitmweb abierto.
  2. Abre una página HTTPS desde el navegador.
  3. Comprueba que aparece una nueva entrada en mitmweb.
  4. Selecciona la entrada.
  5. Revisa las pestañas de solicitud y respuesta.

Deberías poder ver:

  • dominio;
  • URL completa;
  • método HTTP;
  • cabeceras;
  • parámetros;
  • cookies;
  • cuerpo de la solicitud;
  • cuerpo de la respuesta.

Si únicamente aparece una conexión sin contenido, o se produce un error de certificado, la instalación todavía no es correcta.

La propia documentación de mitmproxy recomienda comprobar la configuración abriendo una página HTTPS y verificando que el flujo puede inspeccionarse.

Parte 5. Capturar solamente la aplicación

Opción A. Captura local por proceso

Las versiones actuales de mitmproxy disponen de un modo de captura local para Windows, macOS y Linux. Este modo puede interceptar todas las conexiones del equipo o limitarse a un proceso concreto.

Cierra la ejecución anterior de mitmweb y utiliza:

mitmweb --mode local

Esto intentará capturar las conexiones salientes de todas las aplicaciones del equipo. Para limitar la captura a un proceso:

mitmweb --mode local:NOMBRE_DEL_PROCESO

Ejemplo genérico:

mitmweb --mode local:miaplicacion

También puede utilizarse el identificador numérico del proceso:

mitmweb --mode local:12345

Atención a los procesos auxiliares

Algunas aplicaciones crean procesos adicionales para:

  • actualizarse;
  • mostrar contenido web;
  • descargar archivos;
  • enviar informes de errores;
  • ejecutar tareas en segundo plano.

Si capturas únicamente el proceso principal, podrías perder esas conexiones. Para una auditoría rigurosa, es preferible capturar todo el tráfico dentro de una máquina virtual limpia.

En Linux, el modo local puede solicitar permisos administrativos y depende de la compatibilidad del kernel.

Opción B. Proxy configurado en el sistema

Cuando el modo local no funcione, puedes mantener el proxy del sistema configurado en:

127.0.0.1:8080

Este método es más sencillo, pero algunas aplicaciones ignoran la configuración de proxy del sistema. Por eso debe complementarse siempre con un monitor de conexiones.

Los procesos auxiliares también deben quedar incluidos.

Parte 6. Registrar una línea base

Antes de abrir la aplicación, registra el tráfico que se produce sin ella.

  1. Limpia la lista de solicitudes de mitmweb.
  2. Inicia también el monitor de conexiones.
  3. Espera entre dos y cinco minutos.
  4. Anota los dominios que aparecen sin que la aplicación esté abierta.
  5. Guarda esta captura como línea base.

La línea base sirve para separar el tráfico del sistema operativo, mitmproxy y otros servicios del tráfico generado por la aplicación.

Después:

  1. vuelve a limpiar la captura;
  2. abre la aplicación;
  3. no realices ninguna acción durante unos minutos;
  4. observa qué conexiones aparecen únicamente al iniciar el programa.

Esta segunda captura corresponde a la prueba de inicio e inactividad.

Parte 7. Ejecutar las pruebas de forma controlada

No hagas todas las acciones seguidas. Realiza una sola acción, observa el tráfico y anota el resultado antes de continuar.

Prueba 1. Inicio

  1. Limpia la captura.
  2. Abre la aplicación.
  3. Espera dos minutos.
  4. Anota todos los destinos y solicitudes.

Esta prueba permite detectar:

  • comprobaciones de actualización;
  • carga de configuración;
  • inicio automático de sesión;
  • telemetría de arranque;
  • identificadores enviados al ejecutar la aplicación.

Prueba 2. Aplicación inactiva

  1. Deja la aplicación abierta sin utilizarla.
  2. Espera entre cinco y diez minutos.
  3. Comprueba si se producen conexiones periódicas.

Esto puede revelar:

  • estadísticas recurrentes;
  • comprobaciones de estado;
  • sincronización automática;
  • conexiones permanentes;
  • telemetría enviada en segundo plano.

Prueba 3. Inicio de sesión

Utiliza una cuenta de prueba y comprueba:

  • a qué servidor se envían las credenciales;
  • si la contraseña viaja dentro de HTTPS;
  • si aparecen tokens de autenticación;
  • qué datos del usuario devuelve el servidor;
  • si la app contacta con servicios distintos del proveedor esperado.

La contraseña no debería aparecer en una URL, en parámetros de consulta ni en registros públicos. Aunque aparezca dentro de una petición HTTPS descifrada, no debe publicarse en capturas.

Prueba 4. Introducción de datos

Introduce un marcador único en cada campo disponible:

AUDIT_CAMPO_NOMBRE_20260712
AUDIT_CAMPO_BUSQUEDA_20260712
AUDIT_CAMPO_DESCRIPCION_20260712

Realiza una acción cada vez y busca ese marcador en las solicitudes capturadas.

Prueba 5. Acceso a archivos

Utiliza la carpeta y el archivo de prueba creados anteriormente. Comprueba por separado:

  • seleccionar una carpeta;
  • abrir un archivo;
  • importar un archivo;
  • iniciar una descarga;
  • iniciar una subida;
  • cancelar la operación;
  • eliminar el elemento de la aplicación.

Busca en el tráfico:

  • nombre del archivo;
  • ruta completa;
  • tamaño;
  • extensión;
  • contenido;
  • hash o huella del archivo;
  • fecha de creación o modificación.

Que una aplicación envíe un archivo cuando el usuario ordena subirlo puede ser normal. Que envíe rutas, nombres o contenido al limitarse a visualizar una carpeta requiere una explicación.

Prueba 6. Cierre

  1. Limpia la captura.
  2. Cierra la aplicación.
  3. Mantén las herramientas funcionando durante cinco minutos.
  4. Comprueba si algún proceso continúa comunicándose.

Esto permite detectar:

  • servicios residentes;
  • actualizadores;
  • tareas en segundo plano;
  • envío de estadísticas al cerrar;
  • informes de sesión.

Prueba 7. Reinicio del equipo

Para una auditoría completa:

  1. reinicia el entorno de prueba;
  2. no abras manualmente la aplicación;
  3. comprueba si se inicia algún componente relacionado;
  4. revisa si existe tráfico antes de abrir la interfaz.

Parte 8. Inspeccionar una solicitud

Selecciona una conexión en mitmweb y revisa cuidadosamente los siguientes elementos.

Host y URL

Comprueba:

  • el dominio;
  • los subdominios;
  • la ruta;
  • los parámetros incluidos después de ?;
  • si la conexión utiliza HTTP o HTTPS.

Ejemplo:

https://api.ejemplo.com/telemetry?user=123&version=4.2

En este caso, incluso antes de revisar el cuerpo, ya sabemos que se están enviando un identificador de usuario y una versión.

Método

Los métodos más habituales son:

  • GET: solicita información;
  • POST: suele enviar información;
  • PUT o PATCH: suele modificar o actualizar información;
  • DELETE: solicita eliminar un recurso.

Un GET también puede enviar datos mediante la URL, las cookies o las cabeceras.

Cabeceras

Revisa especialmente:

Authorization
Cookie
User-Agent
Referer
Origin
X-Device-ID
X-Client-ID
X-Request-ID

Los nombres exactos pueden variar. Las cabeceras pueden contener:

  • tokens;
  • identificadores persistentes;
  • información del sistema;
  • versión de la app;
  • idioma;
  • arquitectura del procesador;
  • datos de sesión.

Cuerpo de la petición

El cuerpo puede presentarse como:

  • JSON;
  • formulario;
  • XML;
  • texto;
  • archivo binario;
  • datos comprimidos;
  • Protobuf u otro formato binario.

Ejemplo JSON:

{
  "event": "app_started",
  "user_id": "12345",
  "os": "Linux",
  "app_version": "1.4.2"
}

En este caso, la aplicación estaría enviando un evento de inicio, un identificador, el sistema operativo y su versión.

Respuesta del servidor

La respuesta no representa información enviada por tu equipo, pero ayuda a interpretar la finalidad de la petición. Puede mostrar:

  • confirmación de recepción;
  • configuración remota;
  • perfil del usuario;
  • instrucciones para la aplicación;
  • identificadores asignados por el servidor.

No utilizar datos reales ni tokens válidos.

Parte 9. Buscar los marcadores

Busca en las solicitudes las cadenas que preparaste al principio:

AUDIT_

Revisa: URL, parámetros, cabeceras, cookies, cuerpo de la petición, cuerpos codificados, respuestas y mensajes WebSocket.

Si aparece AUDIT_ARCHIVO_SECRETO_20260712.txt, la aplicación ha transmitido el nombre del archivo. Si aparece AUDIT_CONTENIDO_NO_DEBE_ENVIARSE_20260712, la aplicación ha transmitido el contenido.

Si no aparece directamente, no significa necesariamente que no se haya enviado. Puede haberse transmitido codificado en Base64, comprimido, fragmentado, convertido a un formato binario, cifrado de nuevo dentro de HTTPS o sustituido por un hash.

Cuando sospeches que un contenido ha sido codificado, calcula o busca también su representación Base64, su hash, una parte corta y distintiva del texto, el nombre sin extensión y el tamaño exacto del archivo.

El marcador demuestra qué acción provocó el envío de ese dato.

Parte 10. Comprobar que no queda tráfico fuera del proxy

Esta es la parte que convierte una simple captura en una auditoría seria. Mantén abierto el monitor de conexiones mientras realizas todas las pruebas. Para cada conexión iniciada por la aplicación, anota:

  • proceso;
  • dominio o IP;
  • puerto;
  • protocolo;
  • hora;
  • volumen enviado;
  • si aparece también en mitmweb;
  • si su contenido ha podido inspeccionarse.

Después compara ambas listas.

Resultado A. La conexión aparece en ambas herramientas

La conexión está detectada y su contenido puede analizarse.

Resultado B. Aparece en el monitor, pero no en mitmweb

Existe tráfico no inspeccionado. Las causas pueden ser:

  • la aplicación ignora el proxy;
  • utiliza un proceso auxiliar;
  • emplea UDP o QUIC;
  • utiliza un protocolo no compatible;
  • establece una conexión TLS que mitmproxy no ha podido interceptar;
  • utiliza certificate pinning;
  • se comunica mediante un servicio del sistema.

No declares que la aplicación ha superado la auditoría hasta resolver o documentar esa conexión.

Resultado C. Aparece en mitmweb, pero parece pertenecer a otro programa

Comprueba la línea base y el proceso responsable. Puede tratarse de tráfico ajeno a la aplicación. Wireshark permite seguir flujos TCP, UDP, TLS, HTTP, HTTP/2, QUIC y WebSocket, aunque el contenido TLS solo puede descifrarse cuando se dispone de las claves necesarias.

Una conexión no explicada impide considerar completa la auditoría.

Parte 11. Problemas que pueden impedir la inspección

Certificate pinning

Algunas aplicaciones no confían en los certificados instalados en el sistema. En lugar de eso, esperan un certificado o una clave concreta. Cuando detectan el certificado de mitmproxy: rechazan la conexión, muestran un error, dejan de funcionar o conectan mediante otro mecanismo.

En ese caso, debes indicar que la conexión ha sido detectada, pero su contenido no ha podido inspeccionarse debido a la validación interna del certificado. No debe concluirse que la conexión es segura ni que no contiene datos sensibles.

Si eres el desarrollador de la aplicación, puedes utilizar una versión de depuración que permita instalar el certificado o registrar los datos antes del cifrado. No modifiques aplicaciones de terceros ni eludas sus protecciones sin autorización.

Cifrado dentro de HTTPS

Una aplicación puede cifrar el cuerpo del mensaje antes de enviarlo por HTTPS. mitmproxy descifrará HTTPS, pero mostrará un bloque de datos todavía ilegible.

En una aplicación propia, la solución es revisar el código que prepara la petición, registrar el contenido antes del cifrado, utilizar una compilación de depuración y documentar el algoritmo y los campos enviados. En una aplicación de terceros, esa comunicación debe marcarse como no verificada.

Protocolos binarios

Algunos programas utilizan Protobuf, MessagePack u otros formatos binarios. Aunque el cuerpo no aparezca como texto, todavía puedes revisar: tamaño, destino, frecuencia, cabeceras, fragmentos legibles, cambios producidos por cada acción y documentación del protocolo, cuando exista.

QUIC y HTTP/3

QUIC utiliza normalmente UDP. Dependiendo de la aplicación y la configuración, el contenido puede no aparecer como una petición HTTP convencional. Si se detecta tráfico UDP no inspeccionado, identifícalo en el monitor, comprueba el destino, intenta determinar si la aplicación puede utilizar HTTP/2 sobre TCP, utiliza Wireshark si dispones de las claves de sesión, y marca la conexión como pendiente si no puedes leerla.

Procesos auxiliares

Una aplicación puede delegar una comunicación en un actualizador, un servicio del sistema, un WebView, un navegador integrado o un proceso de informes de errores. Por eso la prueba más sólida consiste en capturar todo el tráfico dentro de un entorno aislado.

Parte 12. Clasificar los datos encontrados

No todos los datos tienen la misma sensibilidad.

Información técnica básica

  • versión de la aplicación;
  • versión del sistema operativo;
  • idioma;
  • arquitectura;
  • resolución;
  • zona horaria.

Puede utilizarse para compatibilidad o telemetría, pero debe comprobarse si está declarada.

Identificadores persistentes

  • identificador de usuario;
  • identificador de instalación;
  • identificador del dispositivo;
  • identificador publicitario;
  • token persistente.

Permiten reconocer al mismo usuario o dispositivo en diferentes sesiones.

Datos de uso

  • pantallas abiertas;
  • botones pulsados;
  • tiempo de uso;
  • búsquedas;
  • errores;
  • descargas iniciadas;
  • funciones utilizadas.

Datos personales

  • nombre;
  • correo;
  • teléfono;
  • dirección;
  • contactos;
  • mensajes;
  • ubicación;
  • dirección IP asociada a una cuenta.

Datos locales

  • nombres de archivos;
  • rutas completas;
  • estructura de carpetas;
  • contenido del portapapeles;
  • programas instalados;
  • procesos en ejecución.

Datos de autenticación

  • contraseña;
  • cookies;
  • tokens;
  • claves de API;
  • claves privadas;
  • códigos de recuperación.

Estos datos requieren especial protección y nunca deben mostrarse sin censura en el informe.

Parte 13. Evaluar cada conexión

Para cada dominio o dirección IP, responde:

  1. ¿Qué empresa o servicio controla el destino?
  2. ¿La conexión es necesaria para una función utilizada?
  3. ¿Se produce únicamente cuando el usuario realiza esa acción?
  4. ¿Qué campos concretos se envían?
  5. ¿Contiene datos personales o identificadores?
  6. ¿La aplicación informa de esta comunicación?
  7. ¿Puede desactivarse?
  8. ¿Continúa produciéndose con la aplicación inactiva?
  9. ¿Se envían más datos de los necesarios?
  10. ¿El contenido ha podido inspeccionarse completamente?

Una conexión no es sospechosa únicamente por dirigirse a un servicio externo. Debe analizarse qué información transmite y con qué finalidad. Del mismo modo, que una aplicación solo contacte con su propio dominio no demuestra que respete la privacidad. Un único servidor puede recibir cualquier cantidad de información.

Parte 14. Documentar los resultados

Utiliza una tabla con estas columnas: acción, proceso, destino, datos enviados, finalidad aparente, resultado esperado e inspección (completa o pendiente). Conserva también:

  • versión de la aplicación;
  • sistema operativo;
  • versión de mitmproxy;
  • fecha y hora;
  • lista de acciones;
  • archivo de captura;
  • capturas de pantalla;
  • configuración utilizada;
  • limitaciones encontradas.

Antes de compartir el informe, elimina o censura: contraseñas, tokens, cookies, claves, correos reales, rutas con nombres personales y contenido privado.

El informe debe distinguir entre lo comprobado y lo que no ha podido verificarse.

Parte 15. Cómo redactar la conclusión

Auditoría completa sin hallazgos inesperados

Durante las pruebas realizadas, todas las conexiones generadas por la aplicación fueron identificadas y su contenido pudo inspeccionarse. No se observó el envío de datos personales, nombres de archivos, rutas locales, contenido de documentos ni telemetría no declarada. Las comunicaciones detectadas se correspondieron con las funciones ejecutadas durante la prueba.

Esta conclusión solo es válida si el monitor de red no mostró conexiones adicionales sin inspeccionar.

Auditoría con comunicaciones no declaradas

La aplicación realizó conexiones adicionales destinadas al envío de estadísticas de uso. Las solicitudes incluían determinados campos. Esta comunicación se produjo en un momento concreto y no se encontró una explicación clara dentro de la aplicación.

Auditoría incompleta

Se detectaron conexiones realizadas por la aplicación cuyo contenido no pudo inspeccionarse. Por tanto, no es posible determinar qué datos transmite ni afirmar que la aplicación no envía información adicional.

No utilices expresiones como "la aplicación no envía ningún dato", "la aplicación es completamente privada" o "la auditoría demuestra que es 100 % segura". Una auditoría de red demuestra lo observado bajo unas condiciones y una versión concretas. Una actualización posterior puede cambiar el comportamiento.

Parte 16. Limpiar el entorno

Cuando termines:

  1. cierra mitmweb;
  2. elimina la configuración de proxy;
  3. desinstala el certificado de mitmproxy;
  4. elimina la máquina virtual o restaura su instantánea;
  5. borra las cuentas y archivos de prueba;
  6. protege o elimina las capturas;
  7. comprueba que la navegación HTTPS funciona normalmente.

No conserves públicamente capturas que contengan tokens o credenciales.

Lista de comprobación final

La auditoría solo puede considerarse completa si puedes responder afirmativamente a todas estas preguntas:

  • ¿La prueba se realizó con una versión concreta de la aplicación?
  • ¿Se utilizaron datos ficticios?
  • ¿Se registró una línea base?
  • ¿Se capturó el inicio, uso, inactividad y cierre?
  • ¿Se incluyeron los procesos auxiliares?
  • ¿Se inspeccionaron solicitudes y respuestas HTTPS?
  • ¿Se buscaron nombres, rutas y contenidos de prueba?
  • ¿Se utilizó un monitor independiente de conexiones?
  • ¿Todas las conexiones del monitor aparecen también en la captura?
  • ¿Se documentaron los destinos y los datos enviados?
  • ¿Se indicaron claramente las limitaciones?
  • ¿Se eliminaron certificados, proxy y datos sensibles al finalizar?

Si alguna conexión no ha podido inspeccionarse, el resultado debe presentarse como auditoría parcial, no como una verificación completa.

Resultado que ofrece este procedimiento

Esta metodología permite determinar, con un alto grado de confianza:

  • con qué servidores se comunica una aplicación;
  • cuándo se produce cada comunicación;
  • qué acción la provoca;
  • qué información contiene cada petición inspeccionable;
  • si se transmiten datos locales o personales;
  • si existe telemetría;
  • y si queda tráfico sin analizar.

La clave no consiste únicamente en interceptar HTTPS. La auditoría se vuelve verificable al comparar el contenido mostrado por el proxy con la lista completa de conexiones observada por una segunda herramienta.

Todo tráfico detectado debe quedar inspeccionado, explicado o marcado expresamente como no verificado.
